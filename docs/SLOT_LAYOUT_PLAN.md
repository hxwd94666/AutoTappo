# 槽位排列开发方案

> 状态：已完成（最终版：四方向 + 换行数量 + v5）
> 目标：把横排/竖排从“好友 ID 绑定坐标”改成“槽位模板 + 运行期分配”。
> 槽位最多 19 个好友位，不包含自己；槽位满后新好友追加到下一个位置。

## 1. 目标行为

- 自己桌宠是排列起点，不占好友槽位；
- 横排、竖排各有独立槽位档案；
- 好友槽位最多 19 个；
- 新好友填编号最小的空槽；
- 19 个槽位都满时，新好友在最大槽位后追加新槽；
- 好友中途离开：把当前最大占用槽位的好友移到空槽，只移动一个；
- 自己的桌宠拖动时，槽位和好友不跟随；
- F5/F6 手动保存时，更新好友当前占用槽位的坐标，不绑定好友 ID；
- 重叠模式保持现有行为，不读写槽位。

## 2. v4 存档

键：

    autotappo-room-layout-v4:<account>:<room>

结构：

    {
      "version": 4,
      "modes": {
        "horizontal": { "slots": [ { "x": 0, "y": 0 }, ... ] },
        "vertical":   { "slots": [ { "x": 0, "y": 0 }, ... ] }
      }
    }

- slots 只保存坐标，不保存好友 ID；
- 默认生成 19 个好友槽；
- 溢出时追加第 20、21 个槽；
- assignments 只保存在内存，重启后按官方好友顺序重新填槽。

旧 v3 数据不再作为好友绑定读取；v4 不存在时按默认规则生成槽位。

## 3. 槽位生成

使用现有 CORE.findSlot 生成，不新增几何算法：

- 以自己桌宠的 visible 矩形为锚点；
- 取第一只在线好友的尺寸作为槽位尺寸；
- 依次生成 19 个槽位，已生成槽位作为 obstacles；
- 横排、竖排分别生成；
- 槽位顺序就是 findSlot 的返回顺序；
- 槽位满时的溢出槽，继续用 findSlot 在当前槽位之后生成。

槽位是绝对坐标，因此自己拖动不跟随。

## 4. 运行期分配

内存结构：

    assignments: Map<catId, slotIndex>

进入房间：

1. 读取 v4 槽位档案；
2. 按官方好友 DOM 顺序，把在线好友依次放入 0..N；
3. 没有槽位档案时先生成 19 个。

新好友：

1. 找编号最小的空槽；
2. 没有空槽则追加槽位；
3. 写入 assignments；
4. 应用坐标。

好友离开，最小变动补位：

1. 删除已离线好友的 assignment；
2. 找最低空槽；
3. 找最高占用槽；
4. 把最高占用槽的好友移到最低空槽；
5. 重复直到没有“中间空槽”；
6. 新好友进入后再填空槽。

只移动离开造成的空槽，不整体重排。

## 5. 模式切换

- 横排/竖排切换时不清空槽位档案；
- 读取目标模式的 slots；
- assignments 按槽位编号复用；
- 立即应用新坐标；
- 如果目标模式还没有槽位，先生成 19 个。

## 6. F5/F6

进入编辑：

- 保留当前 assignments；
- 恢复官方拖拽；
- 不写 v3。

保存：

- 对每个在线好友，读取当前 shell 坐标；
- 用它的 assignment 编号更新对应槽位；
- 空槽位不变；
- 保存 v4；
- 重新应用。

槽位不绑定好友，因此下次新好友可以填这个槽位。

## 7. 重置

清除当前房间 v4 槽位档案：

- 横排/竖排都回到默认生成；
- 清空 assignments；
- 按当前在线好友重新填槽。

## 10. 风险

- v3 旧布局不迁移，首次升级会重新生成；
- assignments 不持久化，重启后好友可能换槽；
- 补位会让末尾一个好友跳到中间；
- 槽位生成依赖当前窗口尺寸和第一只好友尺寸；
- 手动布局在 CSS fallback 环境下可能无法精确拖拽。
